上述病斑需由现场或合格标注者确认，不能拿模型自己生成的名称当真值。健康外观不代表排除隐性感染；局部图片也不要求模型机械返回某一状态。遇到证据不足，应允许 uncertain 或作物未核实，不能依赖用户选择强行宣称 matched。

每列检查要点：

- 健康外观：有足够视觉证据才可 matched；healthy 不带 disease_name/候选百分比。
- 病害证据：suspected_disease 仅列 1–3 个有依据候选，首项与 disease_name 一致，可能性降序且名称不重复；保留未经校准的模型估计说明。证据不足可 uncertain，不强求病名。
- 不清晰/局部近照：作物不能独立核实时 detected 为 null、verification 为 unverified，页面突出“按你选择的{作物}分析”和“图片无法独立确认作物”；reason 说明不足，必要时建议补拍整株。
- 错配：有明确其他受支持作物证据时 mismatch + crop_mismatch，detected 为另一 ID，disease_name 为 null、候选及 possible_causes 为空，提示重新选择。
- 不支持：明确范围外时 unsupported + unsupported_crop + detected other，不产生病害结论或原因列表。大白菜明确排除小白菜和甘蓝；无法区分时保留不确定性。
- 安全：使用微信官方允许的受控测试方法，分别覆盖输入描述、规范化图片及输出全部嵌套文本（含 crop.reason）。违规只显示“您提交的内容含违规信息。”，清空照片、描述、结果与预览许可。不回显命中词/原始文本。输出拦截可先用隔离替身，不记录为真实微信通过。
- 取消：四个阶段退出后无晚到 UI 更新、无自动重发或付费重试；取消只停止客户端，已受理任务可能继续。选择相册期间和识别期间不能改作物；正常完成后改作物保留本地照片/描述，清除结果/许可/错误/进度。

额外接口负例：遗漏/非法 crop_id 在登录前被客户端拒绝；后端返回 INVALID_REQUEST。替身最终结果故意回显不同 selected、加入未知字段、破坏状态关系，客户端必须给固定 INVALID_MODEL_RESPONSE 且不展示照片和结果。确认 v2 POST 只受理 202、v2 GET 使用 Bearer、token 不进入 URL/日志/UI，v1 旧客户端仍能使用原契约。

## 首批有标注样本与指标

先收集小规模、按六作物及上述场景分层的有授权样本。记录匿名样本 ID、crop_id、真实作物、部位、拍摄环境、清晰度、症状、标注依据和标注者；必要时记录现场/实验室确认及争议。先试标注并复核定义，区分“可见健康”“已确认病害”“证据不足”，不能把所有黄叶/斑点都标为病害。训练/提示调整样本与最终保留集分开，同一植株、连拍或近重复图不得跨集合。

每次评估保存代码版本、模型设置标识（不含密钥）、提示版本、日期、样本量/分布和去标识化输出。报告各作物而非只汇总的结果：作物判断混淆表、matched 错认率、unverified/uncertain 比例、错配与不支持作物检出情况；有可靠病害真值时统计健康误报率、病害候选 top-1/top-3 命中及误诊漏诊示例。给出分母、不可评估样本与样本不足限制，区分响应结构正确率和诊断正确率。记录检测失败、超时、取消、响应时延、调用次数/成本；失败样本不得静默剔除。

百分比是未经校准的模型估计，不能直接当作诊断准确率或可靠概率。只有足够样本且标注可比较时再分析分层校准，不用一张图或几个案例宣称提升。当前所有实测数量与指标均未填写，待实际执行后记录，不预填通过率。

## 后续提示比较

建立首批基线后，再比较提示版本。保持模型、图片规范化、解码设置、检测链路和同一保留样本集一致，只改变待比较提示；事先定义作物错认、无证据确诊、病害命中、拒答与耗时/成本等评价项。评审时尽量隐藏版本标签，对错误案例做复核；报告改进与退步及每作物样本量，不能只选成功案例。单次候选结果来自一次请求，不自动付费重试；任何实际模型比较需由操作者另行安排调用预算与执行。提示变更后仍须跑 v1/v2 结构、安全与前端回归，再经过同样的后端优先发布流程。

建议记录模板：日期、代码/提示版本、匿名样本 ID、所选/真实作物、预期范围、verification/detected/status、病害标注与输出、门禁/取消观察、结果与问题。不要保存 Secret、登录 code、job token、图片能力 URL、原始违规内容或可识别个人信息。
